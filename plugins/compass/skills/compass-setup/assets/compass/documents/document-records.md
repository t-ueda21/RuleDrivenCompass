# 工程文書の書き方と確認

## 読者に伝える順序

長い文書では、タイトルの直下に要点を書く。要件定義書なら決まった仕様、試験書なら合否と残る問題を示す。回答が必要な場合だけ、確認してほしい点を添える。RDCのMarkdownでは、この要点を `>` で始まる段落にすると、Excelでも「タイトル」シートに載る。

- **本文**には、誰が何をするとどうなるかを書く。操作を確認した人と採用を決めた人が違えば、それぞれの主語を明記する。
- **表**では、前提・操作・結果をそれぞれの欄に書く。例えば時刻変更の試験なら、操作は「10:00から10:30に変更する」、結果は「確定前に受取日と10:30が並ぶ」と書ける。例示の値と仕様の制限は区別する。
- **根拠**は一か所に記録する。同じ回答が複数の行に関係するときは、各行に結論と課題IDを書く。原文は課題管理表へのリンクから確認できるようにする。

記入済みの文書からは、テンプレートの記入案内を外す。短くする際も、適用条件・例外・数値・未確認の理由・初回の試験結果は残す。

## テンプレートへの記録

必須欄と補足欄を確認する。導入先の書式を使う場合は、各項目の記録先と根拠を確認する。

| 区分 | 記録の基準 |
| --- | --- |
| 必須 | 条件・結果、または根拠の参照先を書く。空欄・仮記入・未確認の項目があれば工程は未完了。 |
| 本番必須・試作必須 | 該当する開発区分の欄に記入する。もう一方の見出しには「対象外（今回はPoC）」などの理由を書く。 |
| 補足・該当時 | 該当する条件と確認結果を書く。記載できない場合は状態と理由を記録する。章全体で同じ場合は、見出しの直下に一度だけ書く。 |

## 適用結果の記録

- 該当なし（対象に外部連携が存在しないことを確認）
- 対象外（今回の依頼は試験書のレビューまで）
- 未確認（検証環境の利用条件が未確定。課題 Q-012）
- 未実施（対象ビルドの配備予定が未確定）
- 判定不能（ログに判定に必要な項目が含まれていない）

未確認・未実施・判定不能の場合は、理由と影響を書く。次の確認先や課題IDが分かれば添える。「状況」と「理由」が別の列にある場合は、それぞれに記入する。

案件固有の内容は、今回の範囲に該当する指定欄に書く。必須項目や完了条件に影響する未確認事項は、工程の完了判定に含める。

## 完了前の確認

単体・結合・総合試験の実行記録は、[試験の初回記録](test-history.md)に従い、初回の判定不能・実施不能とその理由も保持する。初回・最終の判定と集計を試験書に記載する。

1. 冒頭だけで今回の結論が分かるかを読む。重要な条件や例外を見つけるために、複数の表を読み比べる必要があれば、該当箇所を直す。
2. 必須欄の内容、要件・設計・試験の関連ID、証跡を照合する。補足欄には記録または理由が必要。
3. 標準Markdownは[記入状況の確認スクリプト](scripts/check_document.py)で確認する。指定書式の場合やスクリプトを使えない場合も、対応欄を同じ条件で確認する。
4. 工程の完了条件を確認し、不足や未確認事項を報告する。レビューのみの依頼では、対象文書と証跡から確認できた結果を報告する。

## 記入状況の確認スクリプト

プロジェクトのルートから実行する。標準テンプレートの見出しと欄を使った Markdown を対象とする。本番・試作で必須欄が変わる工程には `--mode production` または `--mode poc` を指定する。Excel出力は記入途中の文書にも使用できる。

```powershell
uv run .compass/documents/scripts/check_document.py requirements-definition docs/requirements.md --mode poc
uv run .compass/documents/scripts/check_document.py integration-testing docs/integration-test.md
```

スクリプトは見出し、表の列、記入値、補足欄の理由の有無を確認する。基本設計では、要件との対応で参照した契約と、契約表の内容・版・確定状況も照合する。記載した根拠の正しさ、参照先の内容、工程の合否は文書・証跡の確認で判定する。

工程の着手と完了を判定するときは、[フェーズゲート](phase-gates.md)で必須欄・適用される完了条件・確認資料の版を照合し、結果を記録する。

要件定義の画面試作では、確認待ちの判断と、採用した要件・判定条件の参照を記入チェックと工程ゲートで照合する。工程ゲートでは課題管理表の該当ID、確認先、回答・決定日、内容と根拠の記録も照合する。実際の操作、本人の発言や採否の根拠、試作の実物はレビューで確認する。画面に関する要件を改訂する場合は旧書式にも該当欄を追加する。
