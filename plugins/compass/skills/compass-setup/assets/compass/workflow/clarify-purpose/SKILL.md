# 目的の確認と既存案の再評価

## 判断に必要な情報

1. 依頼の原文・会話・既存資料から、誰が何に使うか、望む結果とその理由、明示された条件を確認する。分類なら「その結果を見て、誰が次に何を決めるか」を特定する。帳票名や項目名、「MECEにして」という手段だけでは用途は確定しない。一件を一人に割り当てる用途と、関係する手続きをすべて選ぶ用途では設計が変わる。どちらかを選ぶ根拠がなければ、分類表の作成・提示は回答後に行う。
2. 各判断に十分な根拠があれば、追加質問を挟まずに進める。必須と指定された手段は守り、目的と食い違う場合は着手前に説明する。手段を任された場合は、既存の情報で目的を達成できるかを確認し、方法・数値をAIが選択する。
3. 目的の解釈や優先順位で結果が変わり、資料でも解消できない場合は、何を決めるための確認かを示し、望む結果とその理由を質問する。会話から考えられる理由を候補として添え、複数・別の理由・訂正を受け付ける。回答までは候補をユーザーの意図・仕様・着手の根拠に使わず、その回答に依存する判断を保留する。
4. 回答後は重要な判断ごとに理由が足りるかを確認する。残る不明点で判断が変わる場合だけ追加で質問する。

例：「この分類で何を決めたい？　一人の担当者を選ぶ用途なら割当の優先順位が必要だよ。変更に関係する確認ルールを選ぶ用途なら、同じ変更に複数のルールを適用できる設計になるよ。両方、または別の用途も教えて。」

## 既存案の要否

「この手順はいらないのでは？」と指摘されたら、元の目的、実際にその手順を使う箇所、削除で改善したい点を確かめる。同じ目的について維持時・削除時の結果を具体例で比較する。理由が足りず結論が変わる場合は、上の手順で確認する。判断を維持するときはその根拠を、変更するときは新しく判明した前提・事実を示す。

## 記録

人間に質問した時点で[課題管理 Skill](../issue-tracking/SKILL.md)に従い、導入先の `.compass/records/issue-log.md` に登録する。回答・決定・反映結果まで同じ課題IDで記録する。AIが選んだ重要な方法や値については、該当工程の既存成果物に、対応する目的・理由、参照資料、選択根拠、検証結果・未確認事項を記録する。成果物を作成しない相談では回答に残す。
