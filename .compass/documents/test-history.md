# 試験の初回記録

単体・結合・総合試験では、各ケースで決めた手順を初めて呼び出す試行を「初回」とする。コマンドの誤り、入力不足、環境障害、ログの読み違いも初回の事実として残す。試験書・Excel・作業後報告には、全件初回合格の場合も、初回と最終の内訳を必ず載せる。

## 1. 計画を固定する

[工程の着手](phase-gates.md)で作業 ID と対象 ID を登録する。アプリの版・実行環境を特定し、試験書の「試験ケース」に全ケースの ID、対応仕様、前提・入力、手順、期待結果を記入する。手順・データ・期待値が外部ファイルにある場合は、その版も固定する。

```powershell
$gate = ".compass/documents/scripts/check_phase_gate.py"
uv run $gate test-plan --work-id change-42 --version build-17 --document deliverables/integration-testing.md --baseline tests/test_inventory_import.py --baseline fixtures/valid.csv
```

`--document` は今回の作業範囲に含まれる全試験工程・全試験書について繰り返し、1回で登録する。単独工程の依頼ではその工程の全ケースを登録する。固定対象の設計・ソース・テストコード・データ・設定・生成処理のファイルには `--baseline` を使う。指定したファイルの内容または欠落状態と、試験書のケース欄が保存される。外部環境は変化を識別できる版を指定する。作業 ID・ケース ID は修正後も継続使用する。

## 2. 最初の操作と結果を直ちに記録する

自動試験は対象ケースの期待値を検査するコマンドを `test-run` に渡す。RDCは起動前に実行 ID を確定し、標準出力・標準エラー・終了状態をその回の証跡に保存する。終了コード0を合格、1を検査不合格、その他の終了コード・起動エラーを判定不能として記録する。この規約に合うテストランナーまたはアサーションを含むテストを使う。異常系のアプリの終了コード自体が期待値なら、その値と副作用を検査するテストを実行する。

```powershell
uv run $gate test-run --work-id change-42 --phase integration-testing --case-id IT-01 --version build-17 -- python -m unittest tests.test_inventory_import.ImportTests.test_valid_csv
```

画面操作や判定が別途必要な試験には `test-begin` と `test-result` を使う。

```powershell
uv run $gate test-begin --work-id change-42 --phase integration-testing --case-id IT-02 --version build-17 --operation "在庫取込手順を実行"
# 表示された実行 ID で実際の操作を行い、直後にその回の出力を保存する。
uv run $gate test-result --work-id change-42 --run-id RUN-000001 --outcome 判定不能 --actual "試験手順のCSV名でファイルを開けず、取消処理まで到達できなかった" --evidence logs/IT-02-first.log
```

実行 ID は台帳が操作前に発行する。例の ID は実際に表示されたものに置き換える。中断した手動試行は同じ ID で観測事実・証跡を記録する。自動試行が強制終了した場合は `test-evidence/RUN-000001.in-progress.log` または中断を示す証跡を `test-result --interrupted` に指定し、判定不能と理由を追記する。テストランナーの自動リトライは初回一巡中は無効にし、ケースごとに初回出力を取得する。まとめて実行する場合も各ケースの操作前に ID を発行し、結果を対応づける。`test-result` の終了コードは台帳への登録の成否を示す。試験の合否は記録された判定で報告する。

| 当初判定 | 記録する事実 |
| --- | --- |
| 合格・不合格 | 試行時の期待結果と実測が一致したか。異常入力の拒否が仕様どおりなら合格 |
| 判定不能 | 誤操作や途中停止など、呼び出した操作、観測結果、製品の判断ができなかった理由 |
| 実施不能 | 前提障害で対象操作を開始できなかった場合の阻害要因、依存先ケース・証跡。前工程のゲートが保留の場合も、`test-begin --blocked` で前提確認に ID を付けて記録できる |

未着手・実行中のケースはその状態で報告する。独立して実行可能な残りのケースをすべて実行し、依存で進めないケースには具体的な理由と証跡を記録する。

## 3. 初回一巡後に修正・再試験する

一巡中は対象版・設計・実装・手順・期待結果・データを固定し、失敗の観測、ログ保存、原因候補の記録を行う。予定した初期状態への復元は元の手順に従う。全ケースで当初判定が揃った時点で初回の内訳を確認し、原因を製品設計、実装、試験手順・期待値、データ・環境、操作などの観点から調べる。原因が確定していない場合は根拠と残る疑問を記録する。実施不能を含む一巡の終了と、工程の通過は個別に判定する。

- **再試験**では、影響ケースと根拠を確認し、修正版・入力・期待結果を試験書に反映する。同じケースの `test-run` または `test-begin` に今回の `--version` と `--reason "原因と変更内容"` を指定する。固定対象ファイルの構成も変えた場合は、更新後の一覧を `--baseline` で指定する。新しい実行 ID に実際の操作と結果を記録する。
- **再判定**は、元の版・手順・データ・期待結果が同一で、当初保存したログだけで読み違いを証明できた場合に使う。`test-rejudge --work-id change-42 --run-id RUN-000001 --version build-17 --outcome 合格 --reason "元の期待値と同じログの観測値が一致する箇所・根拠"` をゲートに指定する。元の実行 ID に再判定を追記し、再実行回数は増やさない。操作を実施できなかったケースには再試験が必要になる。

## 4. 初回と最終を報告する

```powershell
uv run $gate test-report --work-id change-42 --phase integration-testing
```

試験書ごとの「実行結果」「初回・最終結果」「判定集計」に出力された3表を転記し、工程の完了判定には各ケースの最終の実行 ID を使う。`finish` は計画から消えたケース、欠けた試行、初回判定・内訳の差異、未確定の最終判定、保存証跡の変更を保留とする。最終不合格が残る対象は、その事実と残存影響を範囲の判定に記載する。工程の完了可否は既存の完了条件とレビューで決める。

作業後報告の例「10件中、初回は合格7・不合格2・実施不能1。手順修正後に3件を再試験して合格。最終は合格10」。再判定があれば、そのケース ID、同じ実行 ID、当初判定と訂正根拠を明示する。

試行時刻・操作・当初判定・再判定は `.compass/records/phase-gates.sqlite3` に追記し、各回のログは `.compass/records/test-evidence/` に内容のハッシュ付きで保存する。試行の開始・結果登録時に、ケース定義と申告した固定対象の版を照合する。実行中に条件差分を検出した場合は、入力された判定・実測・差分理由を保存し、当該試行の製品判定を「判定不能」とする。手動操作や外部環境の実態は、記録した事実とレビューでも照合する。

既存の試行は `start` のやり直しや中断後にも参照できる。自動試験のコマンド自体が起動できなかった試行・中断として回収した試行は、新しい実行 ID で再試験する。

旧版の台帳は `status` で従来の工程状態と「初回記録なし」を表示する。履歴のない過去分は「初回不明」と報告し、後日の試験は旧作業 ID を参照する追加計画として、元の結果と併記する。旧版の試験書から新しい試験を計画するときはケース ID を引き継ぎ、新書式の実行結果・初回と最終の結果・判定集計を使用する。
