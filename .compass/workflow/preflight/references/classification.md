# 作業前４項目の判定基準

## 各行の決め方

| 表示項目 | 記入する内容 |
|---|---|
| 作業対象 | 共通スキルやルールを作る・変えるなら「Compass 自身の開発・改良」。導入先のアプリや固有設定を扱うなら「導入先プロジェクトの作業」。両方を含む場合は作業単位を分けて示す。 |
| 開発区分 | 実現可能性の確認を目的とする案件は「試作（PoC）」。実利用・運用に供する案件は「本番」。判断できないときは「未確認」。 |
| 作業範囲 | 今回依頼された工程を示す。単独工程は「調査」「詳細設計」「リリース」などの工程名、連続する工程は「実装〜単体試験」のように記載する。離れた工程は個別に列挙する。 |
| 作業内容 | 今回の作業に関係する技術・ツールを複数記載できる。技術を特定できないときは「未確認」、技術を使わない作業なら「該当なし」。 |

- 試作の工程は **要件定義 → 実装 → 総合試験**。
- 本番の工程は **調査 → 要件定義 → 基本設計 → 詳細設計 → 実装 → 単体試験 → 結合試験 → 総合試験 → リリース**。基本設計書と詳細設計書は各設計工程の成果物。リリースでは必要な成果物と README などの利用資料を作成・更新し、利用できる完成状態になっていることを最終確認する。
- 案件の工程表は今回の依頼範囲を判定するために使う。たとえば試作の実装だけを依頼された場合、作業範囲は「実装」。
- 単独の調査・保守・リリースを依頼された場合は、作業範囲に該当する名称を記載する。開発案件から独立した依頼の開発区分は暫定で「適用外」、開発案件の一部で区分が不明なら「未確認」とする。

## 適用する Skill・ガイド・ルールを選ぶ

1. 開発区分と作業範囲に対応する [工程 Skill](../../phase/README.md) を選ぶ。
2. 作業内容に記載した技術・ツールのガイドを選ぶ。ガイドの追加は工程から独立して扱う。
3. 直接扱う箇所と影響先を確認し、適用条件に該当する確認ルールをすべて選ぶ。既存データへの制約追加と公開 API の応答変更が重なる場合は、データ移行と API 互換性の両方を確認する。

対応する資料が未整備なら、プロジェクトの既存指示・仕様・検証手順を参照する。作業中に判明した技術や影響で適用条件が変わった場合は、該当する参照先を選び直す。
