# 要件定義の画面試作

利用者に画面を操作してもらい、その回答を要件に反映する。本番・PoCの両方で、画面の新設・変更や操作性の確認に使う。APIやバッチだけの案件は、要件定義書に対象外の理由を書く。

## 1. 操作できる画面を作る

1. 誰が何を達成したいか、どの操作で何を確かめるかを決める。既知の部分から作り、仮の表示・値・動作は提案と明記する。
2. 表示項目・入力欄・ボタン・結果メッセージを操作順に配置する。利用者が入力から結果の確認まで試せるようにする。判断に関係するエラー・空状態・取消も再現する。
3. 架空のデータで保存や送信を模擬し、自分で対象の操作を試す。

導入先のプレビュー環境や部品があれば使う。配置の指定がなく、単体HTMLで試せる場合は `prototypes/requirements/<機能名>/index.html` に作る。試作ファイルは対象の依頼時に作成する。再提示に備え、コミットや版別ファイルから前の版を開けるようにする。

試作間の移動は操作を試す分だけ用意する。正式な画面遷移図、遷移条件と遷移先の確定は[基本設計](../../basic-design/SKILL.md)で扱う。

## 2. 利用者に操作してもらう

画面名・版・リンクまたはファイルと、試してほしい操作を伝える。起動手順があれば添える。「どの操作で何に困ったか」「どうなると業務を完了できるか」をチャットか案件の既存の手段で返してもらう。

提示時に[課題管理表](../../../issue-tracking/SKILL.md)に確認事項を登録する。[要件定義書](../references/template.md)には次の2点を記録する。

- 「要求の情報源」に「画面試作」と提示版の参照先を書く。
- 「画面試作とフィードバック」に操作・版・課題IDを書き、判断を「確認待ち」にする。

自動操作はAIの検証として記録する。利用者の操作・発言・同意は、本人から確認できた事実を書く。

## 3. フィードバックを要件に反映する

同じ課題IDに確認者・日付・版・実際の発言や観察・判断理由を記録する。採否や優先順位が曖昧なら確認する。要件定義書からその記録を参照する。

| 利用者の回答 | 対応 |
| --- | --- |
| 採用 | 要件を追加・更新する。本番は前提・操作・期待結果、PoCは確認方法と観測できる成功条件を書く。レビュー行に要件IDと条件IDを記録する。条件が複数なら行を分ける。 |
| 修正して試したい | 画面を更新し、変更点・版・操作手順を伝える。判断は「再確認待ち」。回答後に同じ行を更新し、各回の版と経緯を課題管理表や改訂履歴に残す。 |
| 変更なし・見送り | 回答と理由を記録する。 |
| 保留 | 課題IDと影響する範囲を記録する。 |

今回の判断がすべて解決したら、試作・要件定義書・課題管理表で、採用した指摘から要件と判定条件をたどれるか確認して工程完了を判定する。回答に依存する要件は、回答が届くまで確定を保留する。[記録例](references/review-example.md)
